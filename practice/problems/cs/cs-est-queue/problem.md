用 M/M/c 排队模型（到达是泊松过程、服务时间是指数分布、c 台服务器共用一个队列）估算排队延迟。实现：

1. `erlang_c(c, rho)`：利用率为 `rho`（每台服务器的平均忙碌比例，`0 < rho < 1`）时，一个请求到达就要排队的概率。记 `a = c * rho`：

   $$P = \frac{\dfrac{a^c}{c!\,(1-\rho)}}{\sum_{k=0}^{c-1}\dfrac{a^k}{k!} + \dfrac{a^c}{c!\,(1-\rho)}}$$

2. `wait_ms(c, rho, service_ms)`：平均排队时间 = `erlang_c(c, rho) * service_ms / (c * (1 - rho))`；
3. `max_utilization(c, service_ms, budget_ms)`：在平均排队时间不超过 `budget_ms` 的前提下，利用率最高能到多少。用二分或扫描求解，精度 0.001，返回保留三位小数的浮点数（达不到就返回 0.0）；
4. `servers_needed(rps, service_ms, budget_ms)`：给定到达率（每秒请求数）和平均服务时间，满足排队预算所需的最少服务器数。利用率 `rho = rps * service_ms / 1000 / c`，`rho >= 1` 时直接不满足。

```python
round(erlang_c(4, 0.7), 3)            # 0.429
round(wait_ms(4, 0.7, 10), 1)         # 3.6
max_utilization(16, 10, 5)            # 0.918
servers_needed(200, 50, 10)           # 13
```

<!-- 题解 -->
Erlang C 公式的直觉：分子是"所有服务器都在忙、还要继续排队"的概率权重，分母是全部状态的权重和。计算时 `c` 稍大阶乘就会很大，但 Python 的整数不会溢出；工程实现里通常用递推来避免大数。

三个结论值得记住：**排队时间随利用率非线性增长**（同样 4 台，利用率 70% 时排队 3.6 ms，95% 时 44.6 ms）；**池子越大越抗**（同样 90% 利用率，1 台排队 90 ms、16 台只要 3.7 ms）；**因此容量规划要按可接受的排队延迟反推利用率**，而不是"机器别闲着"。

推理服务还要多想一层：这里的"服务时间"方差很大（一个请求可能是 100 token 也可能是 100000 token），指数分布已经算温和的了，真实的 p99 比模型更差；而且引擎内部的连续批处理让"一台服务器同时处理多个请求"，需要把 c 理解成"并发槽位数"。
