按 vLLM 的 `ShmRingBuffer` 的协议实现一个单写者、多读者的广播环形缓冲区 `Ring(n_readers, n_chunks)`（这里在一个进程里模拟，不涉及真正的共享内存）。每一块有一组标志，存在 `self.meta` 里（一个 `bytearray`，第 `i` 块的标志从下标 `i * (1 + n_readers)` 开始：第一个字节是写标志，后面每个读者一个读标志），所有标志初始为 0。

- `try_write(payload) -> bool`：写者按顺序使用第 `0, 1, 2, …` 块（循环）。当前块的写标志为 0（还没写过），或者所有读者的读标志都为 1（大家都读完了），才能写：先把写标志清 0，存入 `payload`，**先**把所有读标志清 0，**再**把写标志置 1，返回 `True`；否则不写，返回 `False`；
- `try_read(reader) -> 数据或 None`：每个读者按顺序读第 `0, 1, 2, …` 块（各自维护自己的位置）。当前块写标志为 1、而且自己的读标志为 0 时，取出数据，把自己的读标志置 1，前进到下一块，返回数据；否则返回 `None`。

修改标志时统一调用 `self._set(index, value)`（模板里已经给出，它会把每次修改记进 `self.log`，测试用它检查修改的顺序）。

```python
r = Ring(n_readers=2, n_chunks=2)
r.try_write("a"); r.try_write("b")
r.try_write("c")          # False：第 0 块还有读者没读
r.try_read(0), r.try_read(1)   # ("a", "a")
r.try_write("c")          # True：第 0 块两个读者都读完了
```

<!-- 题解 -->
这套协议不需要锁：写者只在"没写过"或"所有人都读完"时改写一块，读者只改自己那个读标志，两边不会同时写同一个字节。关键在写者更新标志的顺序：写完数据后先把读标志清零、最后才把写标志置 1。如果反过来先置写标志，读者可能在这两步之间看到"写标志为 1、自己的读标志还是上一轮留下的 1"，误以为已经读过这一块，从而漏掉这条消息。真实实现里读写标志之间还要加内存屏障（vLLM 用"拿一次锁再放掉"实现），保证数据和标志的可见顺序。

写者被最慢的读者卡住（所有读者都读完才能覆盖）也是这个设计的本意：调度结果必须送到每一个 worker，缓冲区满了就等。
