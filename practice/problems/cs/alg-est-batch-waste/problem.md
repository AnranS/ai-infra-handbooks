一个批次要跑到**最长的请求**结束，短请求的槽位就空着。实现：

1. `batch_waste(lengths)`：一个批次里浪费的 token 槽位数 = `最长 × 个数 - 总和`；
2. `total_waste(requests, batch_size)`：按给定顺序切成若干批（最后一批可能不满），总浪费；
3. `sorted_waste(requests, batch_size)`：先按长度排序再切批的总浪费；
4. `waste_ratio(requests, batch_size, sort_first=False)`：浪费占"总槽位"的比例（总槽位 = 浪费 + 有效 token）。

```python
batch_waste([500, 20])                                  # 480
total_waste([500, 20, 480, 30], 2)                      # 930
sorted_waste([500, 20, 480, 30], 2)                     # 30
round(waste_ratio([500, 20, 480, 30], 2), 3)            # 0.475
```

<!-- 题解 -->
这道题量化了一件在推理部署里很关键的事：**把长度相近的请求放进同一批**能大幅减少浪费。例子里按到达顺序分批浪费 930 个槽位，按长度排序后只剩 30。

真实系统当然不能随便排序（会破坏公平性、增加等待），所以实际做法是：连续批处理（请求一结束就立刻换新的进来，浪费只发生在一步之内）、按长度分桶路由、以及用 CUDA Graph 的分桶让批次形状对齐。估算时这个模型可以帮你判断"要不要按长度分组"。

注意浪费的是**计算和显存槽位**，不是生成的 token——decode 阶段每一步所有请求都要算一遍，短请求提前结束之后它的槽位在这一步里仍然被占着（直到调度器替换掉它）。
