实现三种负载均衡策略，并在同一组请求上比较它们。所有随机都用传入的 `rng`（`random.Random` 实例），且**按题目给的顺序**调用，否则结果对不上。

- `round_robin(i, n)`：第 `i` 个请求（从 0 开始）发给第 `i % n` 台；
- `least_conn(inflight)`：发给 `inflight` 列表里值最小的那台，并列时选下标最小的；
- `p2c(rng, inflight)`：调用两次 `rng.randrange(len(inflight))` 得到 `a`、`b`，返回其中 `inflight` 更小的那台；相等时返回 `a`；
- `simulate(policy, costs, n, seed)`：`costs` 是每个请求的处理耗时（按到达顺序，每毫秒到达一个请求，第 `i` 个请求在第 `i` 毫秒到达）。每台服务器串行处理分给它的请求。`policy` 是 `"rr"`、`"lc"`、`"p2c"` 之一，选服务器时用"当前正在处理或排队的请求数"作为 `inflight`。返回每个请求的**排队等待时间**列表（开始处理的时刻减去到达时刻）。

```python
simulate("rr", [5, 5, 5, 5], n=2, seed=0)     # [0, 0, 3.0, 3.0]
```

<!-- 题解 -->
`simulate` 只需要维护每台服务器"忙到什么时候"（`busy_until`）和"还有几个请求在手上"（到达时间小于 `busy_until` 的那些）。第 `i` 个请求在时刻 `i` 到达，先按当前时刻把已完成的请求从计数里去掉，再按策略选一台，开始时间是 `max(到达时间, busy_until[s])`。

三种策略的差别只在"选谁"：轮询和随机完全不看后端状态，一台机器碰上慢请求，后面派给它的请求全都跟着等；最少连接把长尾的影响限制在它自己身上，但需要知道所有后端的实时状态；二选一只随机看两台、选较空的，效果接近最少连接，而且多个负载均衡器实例之间不会同时涌向同一台。

工程上还要注意：真实的"负载"不等于连接数。推理服务里一个请求可能是 100 token 也可能是 100000 token，用"待处理 token 数"做指标比连接数准得多。
