草稿模型一次给出每个请求 $K$ 个位置的草稿，还为每个位置估计了一个置信度（前面都被接受的条件下，这个位置被接受的概率）。
负载高时，验证所有草稿会和真实 token 抢算力，于是要决定**每个请求验证前几个位置**。

- 第 $i$ 个位置（从 1 开始）的**存活概率** = 置信度的前缀乘积 $c_1 c_2 \cdots c_i$，它就是"验证到这个位置时，期望多得到的 token 数"；
- 一步的耗时 = `draft_time + step_time(n)`，`n` = batch 里的请求数 + 放行的草稿位置总数（每个请求本来就要算 1 个 token）；
- 一步期望产出的 token 数 = 请求数 + 放行位置的存活概率之和。

实现：

1. `survival(conf)`：一行置信度 → 存活概率列表；
2. `plan(confs, step_time, draft_time)`：`confs` 是每个请求的置信度列表（长度都是 $K$）。所有请求的所有位置按存活概率从高到低排序，依次放行前 $b$ 个（$b$ 从 0 到全部），选让"期望 token 数 / 一步耗时"最大的 $b$（相同时选较小的 $b$）。返回每个请求放行的位置个数（列表）。存活概率相同的位置，先放行请求编号小的、再按位置从前到后。

```python
confs = [[0.9] * 4, [0.5] * 4]
plan(confs, lambda n: 1.0, 0.1)            # [4, 4]：访存受限，多算几个 token 几乎不花时间，全部验证
plan(confs, lambda n: 0.4 * n, 0.0)        # 算力受限，只放行存活概率高的位置
```

<!-- 题解 -->
- 同一个请求的存活概率沿位置单调不增，所以按得分排序放行的，总是每个请求的一段前缀——和验证的语义一致（前面被拒绝，后面验证了也没用）；
- 放行的多少由代价模型决定：访存受限时 `step_time` 几乎不随 token 数增长，全部验证；算力受限时每多一个位置就要多一份时间，只有存活概率足够高的位置才值得；
- vLLM 的自适应验证（DSpark 的置信度头）就是这个思路，代价曲线在启动时对捕获好的 CUDA Graph 实测得到。
