decode 大多受带宽限制，图级编译器最重要的优化是融合：让中间结果留在寄存器里，不写回显存再读出来。计算图用一个列表描述，按拓扑序给出每个节点 `(名字, 种类, 输入名字列表, 输出字节数)`，种类是 `"input"`（图的输入）、`"pointwise"`（逐元素）、`"reduce"`（归约）、`"matmul"`（矩阵乘，不参与融合）。没有被任何节点使用的节点是图的输出。实现：

1. `eager_bytes(graph)`：不融合时，每个非 `input` 节点读它全部输入的字节、写它自己的输出，返回总字节数；
2. `fused_bytes(graph, group)`：`group` 是一组节点名，融合成一个 kernel 后：只读组外的输入（每个只读一次），只写"被组外使用或者是图输出"的节点；
3. `fusion_groups(graph)`：把 `pointwise` 和 `reduce` 节点分成若干组：两个可融合的节点之间有边（一个是另一个的输入）就在同一组，`matmul` 和 `input` 把图隔开。返回组的列表，每组是节点名的列表（按拓扑序），组之间按组里第一个节点的拓扑序排列；
4. `plan_bytes(graph)`：按 `fusion_groups` 融合后整张图的访存：每组按 `fused_bytes` 算，`matmul` 节点按 `eager` 的方式算（读全部输入、写输出）。

```python
graph = [("x", "input", [], 64), ("sq", "pointwise", ["x"], 64), ("s", "reduce", ["sq"], 4),
         ("y", "pointwise", ["x", "s"], 64)]
eager_bytes(graph)                      # 64+64 + 64+4 + 68+64 = 328
fused_bytes(graph, {"sq", "s", "y"})    # 读 x 64 字节、写 y 64 字节 = 128
```

<!-- 题解 -->
eager 的账：每个算子都把输入从显存读进来、把输出写回去，中间结果至少走两遍显存。融合之后只剩"外部输入读一次、对外可见的输出写一次"：正文里的 RMSNorm + SiLU + 乘法，8 个算子逐个执行共 1.59 MB，融合成一个 kernel 只要 0.41 MB，约四分之一。

分组就是在"可融合节点"构成的子图上求连通分量（沿边的方向无关），用并查集或者 BFS 都可以。矩阵乘把图隔开：它的前后各自成组——真实编译器还会把逐元素运算作为 epilogue 融进矩阵乘（偏置、激活、量化），也会因为寄存器压力、重复计算而放弃一些融合，所以真正的决策由代价模型驱动；这里只算访存的上限。一个中间结果同时被组内和组外使用时，它仍要写回显存，这是 `fused_bytes` 里"被组外使用"那条规则的来源。
