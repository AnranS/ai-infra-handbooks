# 阶段一的里程碑：同样的输出，正式的结构

<p class="lead">阶段一的六章把第 0 步那 126 行里的每一个朴素部件换成正式的模块：<code>Req</code> / <code>Batch</code> / <code>Context</code>、不依赖 <code>nn.Module</code> 的算子层、流式加载的模型、分页的 KV 池、可插拔的注意力后端、带采样器的 <code>Engine</code>。这一页先把阶段结束时的样子跑给你看——同一个提示词、同样的 16 个 token，外加骨架做不到的一件事：4 个请求放进一个 batch，一步算完。六章读完，回来对照这里的数字。</p>

**这一阶段结束时你手里有什么**

- 一个 `Engine`：给它一个填好字段的 `Batch`，返回每个请求的下一个 token；
- 还没有调度器——batch 的字段靠自己填（正是阶段二要自动化的那几行）；
- 单个请求和第 0 步一样快，多个请求一起算时吞吐是第 0 步的三倍；
- 每一步的输出仍然和 Hugging Face 逐 token 一致。

## 读这几个数字

**单个请求：23.7 tokens/s，第 0 步是 25.6。** 正式结构在单请求上**不占便宜**，甚至慢了一点。这不意外：分页 KV 的写入是按位置散写的，注意力后端要为每个请求切出自己的那段 KV，`Req` / `Batch` 的记账也都是 Python。这些开销换来的东西在单请求的数字里看不到——它们是为下面那一行准备的。

**4 个请求一个 batch：每步 57 ms，只比单请求的 42 ms 慢 36%，合计 70 tokens/s。** 这是第 0 步的骨架**做不到**的事。decode 是访存密集的：一步要把 2.4 GB 的 fp32 权重从内存读一遍，矩阵乘的"批"是 1 行还是 4 行，读权重的代价几乎一样。所以把请求攒成 batch，每一步多出来的只是那点计算，权重只读一次。这就是连续批处理的全部道理，推理系统的吞吐都从这里来。

**KV 池写了 79 页，没有任何拷贝。** 第 0 步每一步都 `torch.cat` 把整段 KV 复制一遍；现在每个 token 只写自己那一页，page table 记着它在哪。单独跑和放进 batch 里跑，第一个请求的 16 个 token 完全相同——批处理不改变任何一个请求的结果，这一点后面每一章的测试都会反复确认。

## 骨架的每一块换成了什么

| 第 0 步 | 阶段一 | 换掉的理由 |
| --- | --- | --- |
| 一个 `ids` 张量、一个 `pos` 张量 | [`Req`、`Batch`、`Context`](core.md) | 多个请求各有自己的长度和状态；模型从全局 `Context` 读当前 batch，`forward()` 不用传参 |
| 四个函数 + 一个权重 `dict` | [算子层：`BaseOP` 与各种 `Layer`](layers.md) | 每个 `Layer` 自己管权重的形状、加载和切分，张量并行时才切得动 |
| `safe_open` 一次读完 | [模型与权重加载](models.md) | 按需流式加载；同一个 decoder 文件装下 Qwen3、Qwen2.5、Llama 3 |
| `list` + `torch.cat` | [KV 池、page table 与 token pool](kvcache.md) | 预分配、按页写、零拷贝；多个请求共用一个池 |
| `einsum` + 显式掩码 | [注意力后端与参考实现](attention.md) | 变长 batch、分页 KV、前缀复用的元数据；GPU 上换成 FlashInfer / FlashAttention |
| `argmax` | [Engine 与采样器](engine.md) | 温度、top-k、top-p 按请求设置，一次批量采样；`Engine` 把上面所有东西按正确的顺序初始化 |

## 怎么读这六章

按顺序读，每章先读自测题、自己写一版、再对照本书和官方的实现、最后跑本章的测试。读完[Engine 与采样器](engine.md)，回来重跑这一页的脚本：`step()` 里那几行"自己填 batch 字段"的代码，你会发现每一行都对应阶段二调度器的一个职责——`positions` 和 `out_loc` 从哪来（页分配）、`cached_len` 为什么会变（前缀缓存）、谁决定这一步哪些请求进 batch（准入控制）。阶段二做的就是把这几行自动化。
