# v0.2：不到四千行的调度核心跑出 3.1 倍

<p class="lead">2024 年 7 月 25 日，SGLang 打出 v0.2.0 并发了一篇博客：在 Llama-70B 上吞吐最高是 vLLM 的 3.1 倍，常常追平甚至超过 TensorRT-LLM；而"核心调度器不到 4000 行 Python"。这一章读 v0.2.0 的代码，找出 3.1 倍的来源：默认开启的 CUDA Graph、动态估计的 <code>new_token_ratio</code> 与撤回机制、连续 decode 与流式的平衡，以及发布前后几天接连进来的 bench_serving、DeepSeek-V2 和分块 prefill。这也是 SGLang 从"论文的运行时"变成"推理引擎"的分水岭：博客里"语言"几乎不再出现。</p>

## 来源一：默认开启的 CUDA Graph

7 月 13 日的 #612 "Enable cuda graph by default" 加了 `cuda_graph_runner.py`（173 行）。`ModelRunner.init_cuda_graphs` 决定捕获哪些 batch：

        assert not batch.return_logprob

关键在三处：输入缓冲区（`input_ids`、`req_pool_indices`、`seq_lens`、`out_cache_loc`、FlashInfer 的 `kv_indptr` / `kv_indices`）在初始化时按最大 batch 分配一次，图里的 kernel 读的永远是这些地址；`replay` 时把实际 batch 复制进缓冲区前部、不足的部分填充（`seq_lens` 填 1、`out_cache_loc` 填 0，让假请求"写到槽位 0"而不出错），回放后把输出截到实际 batch；所有图共用一个内存池（`graph_memory_pool`），不同 batch 大小的图不重复占显存。捕获前先跑两遍预热（`for _ in range(2): run_once()`），让 FlashInfer 的 plan 和 PyTorch 的缓存分配稳定下来。

![图：CUDA Graph 回放时的 batch 填充](../assets/figures/sgl-cuda-graph-pad.svg){.aig-svg}

decode 一步只有几十毫秒甚至几毫秒，却要发射几百上千个 kernel；Python 逐个发射的开销在小 batch 时能占到一半以上，CUDA Graph 把它压成一次 `replay()`。这是 v0.2 在小 batch、低延迟场景下赢 vLLM 最多的原因之一（vLLM 当时也有 CUDA Graph，但默认关闭、且和它的 block table 配合得更复杂）。

## 来源二：动态的 new_token_ratio 与撤回

初版的准入用固定系数 0.4 估计运行中请求还会生成多少（[第二章](../origins/first-commit.md)）。v0.2.0 把它变成一个随运行调整的量：

```python title="python/sglang/global_config.py @ v0.2.0 L18-31" linenums="18"
        # Runtime constants: New generation token ratio estimation
        self.init_new_token_ratio = 0.7
        self.base_min_new_token_ratio = 0.2
        self.new_token_ratio_decay = 0.001
        self.new_token_ratio_recovery = 0.05

        # Runtime constants: The threshold (number of tokens) to trigger layer-wise cuda sync.
        # This can improve the speed for large batch sizes during prefill.
        self.layer_sync_threshold = 8192

        # Runtime constants: others
        self.num_continue_decode_steps = 10
        self.retract_decode_steps = 20
        self.flashinfer_workspace_size = 192 * 1024 * 1024

    def forward_decode_batch(self, batch: Batch):
        # Check if decode out of memory
        if not batch.check_decode_mem():
            old_ratio = self.new_token_ratio

            retracted_reqs, new_token_ratio = batch.retract_decode()
            self.new_token_ratio = new_token_ratio

            logger.info(
                "decode out of memory happened, "
                f"#retracted_reqs: {len(retracted_reqs)}, "
                f"#new_token_ratio: {old_ratio:.4f} -> {self.new_token_ratio:.4f}"
            )
            self.forward_queue.extend(retracted_reqs)
        else:
            self.new_token_ratio = max(
                self.new_token_ratio - self.new_token_ratio_decay,
                self.min_new_token_ratio,
            )
```

准入时的估计公式没变（可用 = 空闲 + 可淘汰 − Σ 剩余 × 系数），变的是系数：开始保守（0.7），每成功 decode 一步就衰减 0.001，直到下限 `min_new_token_ratio`（按模型上下文长度换算，默认 0.2）——请求跑得越久、系统越确信"大多数请求不会用完 max_new_tokens"，就越敢多接。估计失败时有后手：`check_decode_mem` 发现 decode 分配不出槽位，就 `retract_decode` 撤回一部分请求（按输出长度排序，撤回最新的），把它们放回等待队列，并把系数调高（`new_token_ratio_recovery`）。撤回的机制 1 月 20 日的 #36 "Fix the possible bug of decode out of memory" 就有了，v0.2.0 把它和系数的升降闭环起来。

这是 SGLang 和 vLLM 调度哲学差别最具体的地方：vLLM "能分配就接收，不够再抢占"，SGLang "预估未来、保守接收、估错了撤回"。两者都能避免死锁；SGLang 的做法在请求长度相近时抢占更少，在长度差异大时更依赖系数的自适应。

## 来源三：连续 decode 与流式的平衡

```python title="python/sglang/srt/managers/controller/tp_worker.py @ v0.2.0 L197-230" linenums="197"
    def forward_step(self):
        new_batch = self.get_new_prefill_batch()

        if new_batch is not None:
            # Run a new prefill batch
            self.forward_prefill_batch(new_batch)
            self.cache_filled_batch(new_batch)

            if not new_batch.is_empty():
                if self.running_batch is None:
                    self.running_batch = new_batch
                else:
                    self.running_batch.merge(new_batch)
        else:
            # Run a decode batch
            if self.running_batch is not None:
                # Run a few decode batches continuously for reducing overhead
                for _ in range(global_config.num_continue_decode_steps):
                    self.num_generated_tokens += len(self.running_batch.reqs)
                    self.forward_decode_batch(self.running_batch)

                    # Print stats
                    if self.tp_rank == 0 and self.decode_forward_ct % 40 == 0:
                        self.print_stats()

                    if self.running_batch.is_empty():
                        self.running_batch = None
                        break

                    if self.out_pyobjs and self.running_batch.has_stream():
                        break
            else:
                self.check_memory()
                self.new_token_ratio = global_config.init_new_token_ratio
```

初版硬编码的"连做 10 步 decode"变成了 `global_config.num_continue_decode_steps`（仍是 10），但多了一个出口：`if self.out_pyobjs and self.running_batch.has_stream(): break`——有流式请求且已经攒出了输出，就提前跳出去发送。这是吞吐（少回 Python 层、少收请求）和流式延迟之间的折中；没有新请求时还会 `check_memory` 自检并把系数重置为初值。真正消灭"连做 N 步"的是 10 月的重叠调度（[第 12 章](../perf/overlap.md)）：CPU 工作被藏到 GPU 后面之后，每步回 Python 层的代价就不再重要。

## 设计取舍

- **CUDA Graph 只给 decode，而且绑定 FlashInfer。** prefill 的形状变化太多，不值得捕获；为了让图可回放，注意力后端必须接受固定缓冲区——这个要求后来成为所有注意力后端的接口约定（`init_cuda_graph_state` / `init_forward_metadata_capture_cuda_graph`）。
- **估计 + 撤回，而不是抢占。** 实现简单（撤回 = 放回队列，KV 还在树里可以命中），但估计系数是全局的，对混合负载不够精细；后来加了 `--schedule-conservativeness` 让用户调它。
- **Python 调度器。** 博客把"Python 实现也能追平 C++"当作卖点。代价要到 batch 很大、每步只有几毫秒时才显现，那是 v0.4 零开销调度要解决的问题。

## 后来怎么样了

- CUDA Graph：捕获的 batch 列表、填充方式和内存池共享沿用至今；2025 年加了 piecewise CUDA graph（#11490，把 prefill 的非注意力部分也图化）和投机解码的图。
- `new_token_ratio` 系列参数今天还在 `global_config.py` 和 `schedule_policy.py` 里，`retract_decode` 仍是显存不足时的第一反应。
- `num_continue_decode_steps` 在重叠调度成为默认后失去意义，相关逻辑被移除。
- `bench_serving.py` 成为 SGLang 和 vLLM 共同使用的压测工具之一，也是本手册[推理系统篇的压测一章](serving://perf/benchmark/)讲的脚本。

## 练习

**1. 填充的代价。** 根据 `replay` 的实现，batch 为 65 时会回放哪张图？浪费多少计算？什么样的 batch 列表能减少浪费、又不让捕获时间和显存失控？

??? success "参考答案"
    向上取整到 72（列表是 1、2、4、8、16、…、128，步长 8），7 个假请求约浪费 10% 的 decode 计算。更密的列表（小 batch 步长小、大 batch 步长大）能减少浪费，代价是捕获时间（每张图几百毫秒）和图的显存；后来的版本正是这样配置的。

**2. 系数的走向。** 假设一批请求都在 2000 步内结束且从未撤回，`new_token_ratio` 的轨迹是什么？如果每 100 步撤回一次呢？

??? success "参考思路"
    从 0.7 每步减 0.001，700 步后到 0.2（下限不低于 `base_min_new_token_ratio` 换算值）；此后保持下限。频繁撤回会反复把系数抬回更高的值（`new_token_ratio_recovery`），系统在"多接"与"撤回"之间震荡，吞吐下降——这就是为什么估计系数要能衰减、也要能恢复。

**3. 验证博客的"不到 4K 行"。** 用 `v020-core-lines.sh` 的结果判断博客的说法指的是哪个范围；把 `mem_cache` 里的 `memory_pool.py` 和 `layers/` 的注意力 kernel 加进去又是多少。

??? success "参考思路"
    controller 目录约 3000 行，符合"不到 4K"；加上 `memory_pool.py`（约 100 行）和三个 Triton 注意力文件（约 900 行）仍在 4K 左右。说法成立，但不包含模型文件和服务层。

!!! interview "怎么讲清楚"
    "SGLang 为什么快？"——不要只答 RadixAttention。按 v0.2 的三个来源讲：CUDA Graph 消灭小 batch 的发射开销；预估 + 撤回的准入让显存用得满又不死锁；连续 decode 减少 Python 层的往返。再补一句"这些都是在 3000 行 Python 里做到的"，以及后来零开销调度把 Python 开销彻底藏起来——这样讲能体现你读过代码而不是博客标题。
